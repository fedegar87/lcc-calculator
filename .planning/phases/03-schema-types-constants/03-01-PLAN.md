**CRITICAL DECISIONS:**
- Use Better Auth model conventions (NOT Auth.js from implementation plan). See 03-RESEARCH.md Pattern 2.
- Use camelCase for all Prisma field names (Prisma convention).
- All monetary values: `Decimal @db.Decimal(14,2)`
- All rates/percentages: `Decimal @db.Decimal(10,8)` (interest, inflation) or `@db.Decimal(8,6)` (maintenance %)
- U-values/physics: `Decimal @db.Decimal(8,4)`
- Use `Json` for nested data (energyPrices, inputs, outputs) -- NOT composite types (MongoDB-only).
- `onDelete: Cascade` from Project down through all relations.
- `@@index` on all foreign keys (variantId, projectId, userId, costItemId).

**Schema sections (in order):**

### AUTH (Better Auth conventions)

<note type="approved_deviation">
**Deviation from locked auth model:** CONTEXT.md locks the User model with `passwordHash` field (Auth.js convention from the implementation plan). This plan uses Better Auth's model conventions instead: password is stored in the `Account.password` field, `Session.token` replaces `Session.sessionToken`, `Session.expiresAt` replaces `Session.expires`, `User.emailVerified` is `Boolean` (not `DateTime?`), and the model is `Verification` (not `VerificationToken`). **Reason:** The project uses Better Auth (not Auth.js) per DEC and STACK.md; using Auth.js field names would cause runtime adapter errors. See RESEARCH.md Pattern 2 for field-by-field mapping.
</note>

- `User` -- id (cuid), name (String), email (unique), emailVerified (Boolean, default false), image (String?), organization (String?), createdAt, updatedAt. Relations: sessions, accounts, projects, memberships, snapshots.
- `Session` -- id (cuid), token (String, unique), expiresAt (DateTime), ipAddress (String?), userAgent (String?), userId -> User (cascade). createdAt, updatedAt.
- `Account` -- id (cuid), accountId (String), providerId (String), userId -> User (cascade). accessToken?, refreshToken?, accessTokenExpiresAt?, refreshTokenExpiresAt?, scope?, idToken?, password? (for email/password auth). createdAt, updatedAt.
- `Verification` -- id (cuid), identifier (String), value (String), expiresAt (DateTime). createdAt, updatedAt.

### PROJECT
- Enums: `BuildingUse` (RESIDENTIAL_SINGLE, RESIDENTIAL_MULTI, OFFICE, EDUCATION, COMMERCIAL, INDUSTRIAL, OTHER), `MemberRole` (OWNER, EDITOR, VIEWER).
- `Project` -- id, name, country?, region?, city?, location?, author?, buildingUse (default RESIDENTIAL_MULTI), constructionYear (Int?), createdAt, updatedAt. userId -> User (cascade). Relations: variants, members, snapshots, revisions, exports. `@@index([userId])`.
- `ProjectMember` -- id, projectId -> Project (cascade), userId -> User (cascade), role (MemberRole, default EDITOR), createdAt. `@@unique([projectId, userId])`, `@@index([userId])`.

### VARIANT

- `Variant` -- id, label (VariantLabel), description?, projectId -> Project (cascade). Relations: geometry?, boundaryCondition?, energyInputs[], costItems[], serviceComponents[], wlcInput?, designCosts[], incomeInput?, maintenanceConfig?. createdAt, updatedAt. `@@unique([projectId, label])`, `@@index([projectId])`.

- `IncomeInput` -- id, variantId (unique) -> Variant (cascade). Flat fields (NOT JSON): rent1MonthlyPerM2, rent1Area, rent1Taxes, rent2*, rent3*, otherIncome1, otherIncome1Taxes, otherIncome2*, otherIncome3*, expectedPricePerM2. All `Decimal? @db.Decimal(10,2)` for per-m2, `@db.Decimal(14,2)` for totals.

<note type="approved_deviation">
**Deviation from implementation plan:** CONTEXT.md locks IncomeInput as `(rents as JSON, otherIncomes as JSON, expectedPricePerM2)`. This plan uses flat fields instead (rent1MonthlyPerM2, rent1Area, rent1Taxes, rent2*, rent3*, otherIncome1*, otherIncome2*, otherIncome3*). **Reason:** Flat fields are preferred because they enable direct SQL queries/filtering on individual rent values, provide compile-time type safety via Prisma's generated types, eliminate runtime JSON parsing/validation overhead, and allow `@db.Decimal` precision annotations per field. The Excel workbook has exactly 3 rent rows and 3 other-income rows, so the fixed structure maps naturally to flat columns. User-approved.
</note>
