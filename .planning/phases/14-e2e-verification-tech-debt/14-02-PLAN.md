## Objective

Verify the complete user workflow end-to-end against the Docker PostgreSQL setup. This is a verification phase — no new features are built. The executor will start the dev server, exercise each flow via the browser-accessible endpoints, and document the results.

## must_haves

- Auth flow verified: register new account, login, logout all work
- Data entry verified: create project, enter data in all 4 input steps (Info, WLC, Construction, Energy)
- Results verified: calculated results display on the Results page
- Export verified: PDF and Excel downloads complete successfully
- Verification report written with pass/fail for each step

## Tasks

<task id="1" title="Verify auth flow (E2E-02)">
<action>
Verify the auth flow works end-to-end. The app should already be running from Phase 13 (Docker + dev server).

1. Ensure Docker is running: `docker compose ps` — PostgreSQL must be healthy
2. Ensure dev server is available: `curl -s -o /dev/null -w "%{http_code}" http://localhost:3001` should return 200 or 302
3. If not running, start them:
   - `docker compose up -d`
   - Wait for PostgreSQL health check
   - `npx prisma migrate deploy`
   - Run seed if needed: `npx tsx prisma/seed.ts`
   - Start dev server in background: `npm run dev &`
   - Wait for server to be ready (poll http://localhost:3001)

4. Test registration: Use `curl` or the Better Auth API to register a new test user:
   ```bash
   curl -X POST http://localhost:3001/api/auth/sign-up/email \
     -H "Content-Type: application/json" \
     -d '{"email":"e2e-test@example.com","password":"TestPass123!","name":"E2E Tester"}'
   ```
   Expect: 200 response with user object

5. Test login:
   ```bash
   curl -X POST http://localhost:3001/api/auth/sign-in/email \
     -H "Content-Type: application/json" \
     -d '{"email":"e2e-test@example.com","password":"TestPass123!"}' \
     -c cookies.txt
   ```
   Expect: 200 response with session

6. Test authenticated access:
   ```bash
   curl -b cookies.txt http://localhost:3001/api/auth/session
   ```
   Expect: 200 response with valid session containing user info

7. Test logout:
   ```bash
   curl -X POST http://localhost:3001/api/auth/sign-out -b cookies.txt
   ```
   Expect: 200 response

8. Verify session is invalidated:
   ```bash
   curl -b cookies.txt http://localhost:3001/api/auth/session
   ```
   Expect: null/empty session

Document results in the verification report.
</action>
<verify>
All auth API calls return expected status codes. Registration creates a user, login returns a session, logout invalidates it.
</verify>
</task>

<task id="2" title="Verify data entry and results (E2E-03)">
<action>
Verify that the seeded demo project has data across all 4 input steps and that calculation results can be retrieved via tRPC.

1. Login as the demo user (created by seed):
   ```bash
   curl -X POST http://localhost:3001/api/auth/sign-in/email \
     -H "Content-Type: application/json" \
     -d '{"email":"demo@lcc.local","password":"demo1234"}' \
     -c cookies.txt
   ```

2. Verify project list is accessible via tRPC. Use the tRPC batch endpoint to call project.list:
   ```bash
   curl -b cookies.txt "http://localhost:3001/api/trpc/project.list?input=%7B%7D"
   ```
   Expect: JSON response with at least 1 project

3. Extract the projectId from the response. Then verify variant data exists by calling calculation.calculate:
   ```bash
   curl -b cookies.txt -X POST "http://localhost:3001/api/trpc/calculation.calculate" \
     -H "Content-Type: application/json" \
     -d '{"json":{"projectId":"PROJECT_ID","variantLabel":"BASE","formulaMode":"excel_bugfixed"}}'
   ```
   Expect: 200 response with LCC calculation results (totalLCC, npv, annual breakdowns)

4. Verify all 3 variants can be calculated (BASE, VARIANT_1, VARIANT_2) by repeating the calculation call for each.

5. Verify the Results page data would render by checking that the calculation response includes:
   - `totalLCC` (number > 0)
   - `annualBreakdown` (array with entries)
   - `componentSummary` (object with cost categories)

Document results in the verification report.
</action>
<verify>
All 3 variants return valid calculation results with non-zero totalLCC, populated annual breakdowns, and component summaries.
</verify>
</task>

<task id="3" title="Verify export (E2E-04)">
<action>
Verify that PDF and Excel exports generate successfully.

1. Login as demo user (reuse cookies from task 2, or re-login):
   ```bash
   curl -X POST http://localhost:3001/api/auth/sign-in/email \
     -H "Content-Type: application/json" \
     -d '{"email":"demo@lcc.local","password":"demo1234"}' \
     -c cookies.txt
   ```

2. Call the PDF export endpoint:
   ```bash
   curl -b cookies.txt -X POST "http://localhost:3001/api/trpc/export.generatePdf" \
     -H "Content-Type: application/json" \
     -d '{"json":{"projectId":"PROJECT_ID","variantLabel":"BASE","formulaMode":"excel_bugfixed"}}'
   ```
   Expect: JSON response with `data` (base64 PDF), `fileName`, `mimeType: "application/pdf"`

3. Verify the PDF data is valid base64 and non-empty (length > 1000 characters)

4. Call the Excel export endpoint:
   ```bash
   curl -b cookies.txt -X POST "http://localhost:3001/api/trpc/export.generateExcel" \
     -H "Content-Type: application/json" \
     -d '{"json":{"projectId":"PROJECT_ID","variantLabel":"BASE","formulaMode":"excel_bugfixed"}}'
   ```
   Expect: JSON response with `data` (base64 XLSX), `fileName`, `mimeType`

5. Verify the Excel data is valid base64 and non-empty

6. Optionally decode the base64 and save to files to verify they are valid PDF/XLSX:
   ```bash
   echo "BASE64_DATA" | base64 -d > /tmp/test-export.pdf
   echo "BASE64_DATA" | base64 -d > /tmp/test-export.xlsx
   ```

Document results in the verification report.
</action>
<verify>
Both PDF and Excel exports return non-empty base64 data with correct MIME types and filenames.
</verify>
</task>
